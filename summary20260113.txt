Lumina PDF Reader 開發工作日誌摘要
日期: 2026-01-13 專案階段: 核心功能完整性達成 (V1.0 Milestone)

本文件記錄了 Lumina PDF 閱讀器後期開發的關鍵歷程，重點聚焦於 PDF 內部連結系統、書籤管理的深度實作，以及使用者體驗的細節打磨。

1. 核心挑戰：PDF 內部連結與跳轉系統
需求目標
實現點擊 PDF 頁面上的連結（如目錄、引用）能正確跳轉到對應頁面。由於 Lumina 支援頁面重組（Import/Merge/Reorder），原始 PDF 的頁碼索引（index）與顯示的虛擬頁面索引不再是一一對應，這帶來了複雜的映射問題。

開發歷程與技術決策
連結數據提取 (Extraction)

最初嘗試: 使用 
lopdf
 解析 Link Annotation。
遇到問題: 
lopdf
 的低階解析過於繁瑣，且與 pdfium-render 的渲染座標系統整合困難。
解決方案: 改用 pdfium-render 的 page.links() API。它提供了標準化的 Link 物件，包含 rect（座標）和 destination（目標）。
座標系統標準化

問題: PDF 的座標系原點在左下角，而網頁（前端）在左上角。且 PDF 頁面可能有旋轉（90/180/270度）。
實作: 實作了座標轉換邏輯，將 PDF 座標標準化為百分比（0.0-1.0），並根據 page_rotation 動態調整 x, y, width, height，確保在前端無論如何縮放都能精確覆蓋點擊區域。
頁面映射 (Page Mapping)

核心難點: 原始 PDF 的 "Go to Page 5" 在經過使用者刪除第 1-3 頁並插入新封面後，目標頁面可能變成了第 2 頁，或者根本不在目前的文檔中。
架構設計: 建立了一套 
VirtualPage
 系统。
後端維護 
(source_path, original_index)
 到 current_virtual_index 的映射表。
連結點擊時，不直接跳轉絕對頁碼，而是查詢「原始文檔的第 N 頁現在對應到哪個虛擬頁面索引」。
2. 核心挑戰：書籤系統與相容性
需求目標
實現書籤的讀取、顯示、修改（重命名），並確保存檔後的 PDF 書籤能在第三方軟體（如 Adobe Reader）中正確顯示。

開發歷程
書籤讀取與顯示

從 PDF 提取書籤樹狀結構，並將其扁平化或映射到目前的虛擬頁面。
設計了 Navigation 面板，區分「Grid 模式（顯示所有頁面）」與「Reader 模式（僅顯示書籤）」。
書籤存檔相容性 (The Compatibility Battle)

問題: pdfium-render (v0.8.x) 對於寫入書籤的支援有限，無法輕易修改現有書籤結構。
策略: 採用「雙引擎」策略。
先使用 pdfium-render 處理頁面的重組、旋轉與內容儲存（生成無書籤的 PDF）。
再使用 
lopdf
 (Rust 的純 PDF 解析庫) 對產生的檔案進行「後處理」，注入書籤結構。
Catalog 與 Outlines 結構修復

深度 Debug: 即使寫入了書籤物件，Adobe Reader 仍無法顯示。
原因: PDF 規範要求 Document Catalog 必須有一個 Outlines 字典指向書籤根節點。
lopdf
 的 build_outline() 建立了結構但未自動更新 Catalog。
解決: 手動獲取 doc.catalog_mut() 並寫入 Outlines 參照。
書籤 vs. 頁面標籤的邏輯釐清

UX 決策: 原本所有頁面都有 "Page N" 的預設名稱，導致書籤面板充滿無意義資訊。
最終設計:
引入 has_bookmark 欄位。只有當 custom_name 被設定（來自原始書籤或用戶修改）時，才被視為「真書籤」。
存檔邏輯: 只保存 has_bookmark = true 的頁面到 PDF 書籤中。確保匯出的檔案乾淨、專業。
3. 體驗打磨：滾動與視圖同步
問題與解決
滾動位置丟失: 從 Grid 切換回 Reader 模式時，閱讀進度會重置。
解法: 放棄基於「頁面索引currentPage」的粗略定位，改用精確的「像素位置 scrollTop」記憶。
無限滾動訊號干擾: 匯入檔案後，程式碼會誤判並不斷強制滾動回去。
解法: 實作 scrollSignal 的一次性消費機制 (onScrollComplete 回調)，滾動完成即清除訊號。
技術架構總結
前端: React + Virtuoso (虛擬滾動) + TailwindCSS
後端: Rust (Tauri)
PDF 引擎:
pdfium-render: 負責高效渲染、頁面操作、連結提取。
lopdf
: 負責低階結構操作（書籤注入、Catalog 修復）。
狀態管理: 採用 
VirtualPage
 中介層，解耦了「原始檔案結構」與「當前編輯狀態」，實現了無損的頁面重組與導航。
結語: 本專案成功建立了一個不僅能「讀」也能「深度編輯與重組」的 PDF 工具，並解決了最棘手的跨軟體相容性問題。
